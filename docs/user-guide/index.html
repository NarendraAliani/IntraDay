What is IntraDay?

IntraDay is a control-plane application for Indian NSE intraday trading — currently a configuration, connectivity, and market-data observation platform, not yet a trading system.

Scope

The project is limited to Indian NSE intraday trading. Since Checkpoint 64.77, the primary trading instrument is NSE stock options, with NSE cash equities retained as supporting/underlying reference instruments. Index options (OPTIDX), BSE options and BSE equities are not enabled. Futures, overnight positions, commodities, currencies, and crypto remain explicitly out of scope. Indices (NIFTY, SENSEX) may appear only as market context, never as tradable instruments.

What exists today

Login / sessions / role-based accessImplemented
Risk / Universe / Strategy version configuration (read + activate)Implemented
Dhan / Telegram / Discord connection settingsImplemented
Read-only Dhan market-quote connectivityImplemented
Live market-data observation (quotes, 1-minute bars)Implemented
Trading-grade OHLC dataNOT IMPLEMENTED — data classified SAMPLE_BAR
Trading signal generationNOT IMPLEMENTED
Paper trading (order state machine, risk engine, kill switch, simulated execution, order-entry UI, order/trade/position monitor)PARTIAL — end-to-end loop implemented and tested; scheduled auto-expiry and an automatic live-price feed remain manual/undone
Order placement / real tradingNOT IMPLEMENTED — LIVE mode does not exist

Before You Start

What this application actually assumes about your computer, verified from the repository's own configuration.

Assumptions

  • Operating system: Windows (the launcher is app.bat, a Windows batch file). The backend/frontend themselves are cross-platform, but the single-click startup path documented here is Windows-specific.
  • Disk space: a few hundred MB for Python/Node dependencies once installed.
  • Network: only needed to install prerequisites and to reach Dhan/Telegram/Discord if you configure them — the app itself runs entirely on your own machine (127.0.0.1).
  • Browser: any modern browser (Chrome, Edge, Firefox). No specific version is enforced by the project.

What you'll need before "First Startup" will succeed

  • Python 3.12 (exact requirement in pyproject.toml: python = "^3.12")
  • Poetry (any recent version — manages the exact Python package versions from poetry.lock)
  • Node.js and npm (any current LTS Node release)
  • PostgreSQL (the project's own local-development guide uses PostgreSQL 16)
  • Git (to have obtained the project files in the first place)
Redis is referenced in the project's configuration (REDIS_URL in .env) for caching/session support, but is not verified as a hard requirement for the exact commands documented in this guide — the authoritative source is docs/development/LOCAL_DEVELOPMENT.md, which documents installing it as optional native software alongside PostgreSQL. If a command in this guide fails with a Redis connection error, install and start Redis the same way as PostgreSQL.

Installation

Every command below is a real command from this repository's own documented workflow (docs/development/LOCAL_DEVELOPMENT.md) — not a generic placeholder.

1. Prerequisite checks

ToolWhy it's neededCheck it's installed
Python 3.12Runs the Django backendpython --version
PoetryInstalls backend dependencies exactlypoetry --version
Node.js / npmRuns and builds the frontendnode --version / npm --version
PostgreSQLStores all persisted application datapsql --version

If any command above says "not recognized" / "command not found", that tool isn't installed or isn't on your PATH — install it (or re-run its installer with "Add to PATH" checked) before continuing. app.bat also checks for these automatically and tells you exactly which one is missing.

2. Backend and frontend dependencies

poetry install                  # installs backend dependencies (pyproject.toml)
cd frontend
npm install                     # installs frontend dependencies
cd ..

app.bat runs both of these for you automatically the first time, if they haven't been run yet.

3. Environment configuration

cp .env.example .env            # backend configuration — never commit this file
cp frontend/.env.example frontend/.env.local   # frontend configuration

Open .env and set at minimum your PostgreSQL password to match your local install. The other values (DHAN_CLIENT_ID, TELEGRAM_BOT_TOKEN, etc.) can stay blank — they can also be configured later through the app's own Settings screen, which is the recommended way. app.bat creates both files automatically from their .example templates if they don't exist yet.

Never commit .env or frontend/.env.local. Both are already excluded from version control (.gitignore). Never paste real credentials into any file that isn't one of these two.

4. Database setup

-- inside psql, using the values from your .env --
CREATE USER intraday WITH PASSWORD 'changeme';
CREATE DATABASE intraday OWNER intraday;
GRANT ALL PRIVILEGES ON DATABASE intraday TO intraday;
ALTER USER intraday CREATEDB;

Then apply migrations (creates all the database tables the app needs):

poetry run python manage.py migrate

app.bat also runs this automatically on every startup — it's safe to run repeatedly (already-applied changes are skipped).

5. Verify before your first login

Once the backend is running (see First Startup), visit http://127.0.0.1:8000/readyz in a browser. It should report both database and cache as "ok". If either says otherwise, that service (PostgreSQL or Redis) isn't reachable yet.

What each startup step means

StepWhat it checks / does
[1/8]Confirms Python and Poetry are on your PATH.
[2/8]Confirms Node.js and npm are on your PATH.
[3/8]Installs backend dependencies if missing (poetry install), creates .env from the template if missing.
[4/8]Installs frontend dependencies if missing (npm install), creates frontend/.env.local from the template if missing.

If something is missing

  • Python missing: the launcher stops immediately at step 1 with a clear message and a link to install it.
  • Poetry missing: same — stops at step 1.
  • Node/npm missing: stops at step 2.
  • PostgreSQL unreachable: step 5 (migrations) fails with a clear message; the launcher stops before starting either server.
  • Port 8000 already in use: the backend window will show a Django error about the address already being in use; the health check at step 6 will then time out after 30 seconds and the launcher will warn you explicitly rather than pretending it succeeded. Close whatever is already using port 8000 (see Troubleshooting) and re-run.
  • Port 5173 already in use: same pattern as above, at step 7.
  • Dependencies missing: steps 3/4 install them automatically the first time — this can take a few minutes, this is expected, not a hang.
Closing the "IntraDay Launcher" window itself does not stop the app — the backend and frontend run in their own separate windows. See Safe Shutdown for how to actually stop them.

Login

The app uses session-cookie based login — the same mechanism as most websites you already use, not a special or complicated system.

What username and password mean here

There is no default account. This is deliberate, so no fixed, guessable password ever ships with the project. If you're setting up your own local copy, create your own account (replace yourname and changeme below with your own values — this is a command you run and choose the password for, not a real shipped credential):

poetry run python manage.py shell -c "from django.contrib.auth.models import User, Group; u = User.objects.create_user('yourname', password='changeme'); u.groups.add(Group.objects.get(name='configuration-operators'))"

This creates an account that can both view and activate configuration (member of the "configuration-operators" group). Omit the u.groups.add(...) line for a read-only account. app.bat itself prints this exact command in its final summary, so you don't need to remember it.

This guide never documents a real password — the changeme above is a placeholder you replace yourself. If someone else manages your environment and already created an account for you, ask them for the username/password directly; it is never written down in this guide or anywhere in the repository.

What happens when you log in

  1. The frontend asks the backend "who am I?" when the page first loads — this also sets a security cookie (CSRF token) used to protect the next step.
  2. You submit your username and password.
  3. The backend checks them and, if correct, starts a session — a small secure cookie your browser now carries automatically.
  4. Every screen after that uses this session to know who you are and what you're allowed to do.

Why CSRF exists

CSRF protection stops a malicious website from secretly submitting requests on your behalf using your logged-in session. It's a standard, expected part of how this kind of login works — not something specific to this project or something you need to configure.

What a 401 means

401 Unauthorized — you're not logged in, or your session has expired. You'll be returned to the login screen.

What a 403 means

403 Forbidden — the request was rejected for a permissions or security-check reason, distinct from "not logged in." On the login screen specifically, a 403 usually means the page loaded before the backend was ready, so the security cookie from step 1 above was never set. app.bat now waits for the backend to be confirmed healthy before you're told the app is ready, specifically to prevent this. If you still see it: reload the page once (this repeats step 1 above) and try again.

Logging out

Use the Sign out button in the top-right of the app once logged in.

Configuration Screens

Two top-level screens exist for configuration, reachable from the navigation bar once logged in: Configuration and Settings. A third, Market Data, is covered separately in Live Market Data Monitor.

Configuration screen

Purpose: view and activate versioned Risk / Universe / Strategy configuration. Who should use it: anyone can view; only users in the "configuration-operators" group can activate a version.

TabWhat it shows
Risk ConfigurationEvery saved version of risk limits (max intraday loss, max position size, max per-trade risk), which one is currently active.
UniverseEvery saved version of the tradable-instrument list.
Strategy VersionEvery saved version of a strategy's specification/code/configuration identity (version bookkeeping). For the actual strategies and their parameters, see Strategies.

Activation behavior: selecting a historical version and confirming makes it the active one; the previous active version becomes historical. Every activation is recorded permanently (audit trail) with who did it and when.

Common errors: a 403 on activation means your account isn't in the operator group — this is enforced by the backend, not just hidden in the interface.

Settings screen

Purpose: configure connectivity for Dhan (broker), Telegram, and Discord. Who should use it: viewing requires only being logged in; saving/testing requires the same operator group as Configuration activation.

Each of the three cards (Dhan, Telegram, Discord) follows the same pattern — see field-by-field detail in Dhan Setup for Dhan specifically; Telegram and Discord follow the identical save/test/status pattern with their own fields (Bot Token + Channel ID for Telegram; Webhook URL for Discord).

Secrets are never shown once saved. Every credential field is always blank when you open the form — leaving it blank and saving means "keep the existing value unchanged." Typing a new value replaces it. This is intentional, not a display bug.

Dhan Setup

Dhan is an Indian stock broker. This application can connect to your Dhan account to read account information and live market quotes — it cannot place, modify, or cancel any order. That capability does not exist in this codebase.

Why the system needs Dhan

Dhan is the only market-data source currently implemented. Without a working Dhan connection, the Market Data screen has nothing to show.

What credential is required

  • Client ID — your Dhan account identifier (not secret, but still shown only partially masked in the app).
  • Access Token — a JWT token from Dhan's own developer portal. This is secret.

Both field names match Dhan's own official API documentation exactly — nothing was invented.

Where it is configured

Open Settings → Dhan. Enter your Client ID and Access Token, then Save. Alternatively, these can be set as environment variables (DHAN_CLIENT_ID, DHAN_ACCESS_TOKEN in .env) as a fallback — the Settings screen always takes precedence once something is saved there.

How credentials are protected

  • Stored encrypted at rest in the database — never in plain text.
  • Never returned by any API response, in any form — not even masked.
  • Never logged.
  • The Settings form always shows the field blank; blank + save = unchanged.

How to verify configuration

After saving, click Test Connection. This performs exactly one real, read-only call to Dhan's account-profile endpoint (never a trading endpoint) and shows the result:

ResultMeaning
ConnectedDhan accepted the credential.
Authentication FailedDhan rejected the Client ID / Access Token combination.
Connection ErrorCould not reach Dhan (network issue, timeout).
Not ConfiguredNo credential is saved yet.
Honest current status: during this project's own development and testing, the Dhan credential present in the local environment was rejected by Dhan (Authentication Failed). This guide does not claim live data is currently flowing — only that the connectivity code path itself works correctly end-to-end. If you see the same result, your credential needs to be checked/regenerated in Dhan's own developer portal — this is not something the application can fix for you.
Never paste your real Access Token into any file in this repository, any chat message, or any documentation — including this guide. Configure it only through the Settings screen or your local .env file (which is never committed to version control).

Market Data Concepts

What the Market Data screen actually shows, and — critically — what its limitations are.

Key terms

Quote
One price reading for one stock at one instant, fetched from Dhan when you click Refresh.
Observation
Every quote the app has ever fetched is stored permanently as an "observation" — a historical record.
1-minute bar
A summary (Open/High/Low/Close) of all observations that fell within one minute.
FORMING bar
The current, still-in-progress minute — its values can still change.
CLOSED bar
A past minute that has fully elapsed — though see the note below about revisions.
OHLC
Open, High, Low, Close — the four prices that describe a bar.
Gap / missing interval
A minute with zero observations — the app reports this honestly rather than inventing a value.

The actual pipeline

Dhan quote (one real HTTP call, only when you click Refresh)
    ↓
Quote normalization (converts Dhan's format into this app's own format)
    ↓
Stored permanently as an observation
    ↓
Aggregation (groups observations into 1-minute bars)
    ↓
Stored as a bar
    ↓
Recent Bars API (read-only)
    ↓
What you see on screen

Why the current bars are SAMPLE_BAR, not trading-grade

Classification: SAMPLE_BAR. NOT TRADING_GRADE_BAR.

This app fetches a price only when you (or an automated process) explicitly ask it to — there is no continuous, always-on price feed yet. Because of that:

  • HIGH may be lower than the true high of that minute — a price spike between two of your clicks is simply never seen.
  • LOW may be higher than the true low, for the same reason.
  • OPEN is only the price at whichever moment happened to be sampled first in that minute — not necessarily the true first trade.
  • CLOSE is the last sampled price, which may be several seconds before the minute actually ended.
  • VOLUME is not calculated at all — Dhan's own volume figure is a running daily total, and safely turning that into "volume traded in just this minute" isn't implemented. The app shows — instead of guessing.

These bars are genuinely useful for watching prices move, testing the app itself, and understanding the system — they are not yet approved for computing trading signals or making trading decisions. Building signal logic on data with these gaps could silently produce wrong, misleading results.

Live Market Data Monitor

The screen reached via the Market Data navigation item. Observation-only — it contains no buy/sell/order/position controls anywhere, by design.

What you'll see

SectionWhat it shows
Market SessionWhether the NSE market is currently Pre-Market, Open, or Closed, based on fixed exchange hours (09:15–15:30 IST). Does not yet account for market holidays.

Reading the badges

  • ● Fresh / ◐ Stale — whether a quote is recent enough to trust as "current."
  • ◐ Forming / ● Closed — whether a bar's minute has fully elapsed.
  • The screen auto-refreshes what it displays every 5 seconds — this only re-reads already-stored data, it never triggers a new call to Dhan by itself.

Why Volume shows "—"

Not a bug or missing feature — a deliberate choice explained fully in Market Data Concepts: fabricating a plausible-looking number would be actively misleading, so the app shows nothing rather than guessing.

This screen requires a working Dhan connection (see Dhan Setup) and, for real data, the NSE market to be open (weekdays, 09:15–15:30 IST).

Strategies

The Strategies screen lets you configure and version the parameters of the built-in trading strategies. It does not place trades — see the callout below.

"Active" does not mean "live trading." Activating a strategy or saving a configuration on this screen only makes it eligible for research, diagnostics, and backtesting against fixture/historical data. It never places an order or authorizes broker execution — that remains governed separately by risk controls and the kill switch, neither of which this screen touches. Live signal execution also remains blocked because current market data is SAMPLE_BAR, not trading-grade.

What a strategy is

A strategy is a small, self-contained rule that looks at recent price bars and computed features (like a moving average) and decides whether the picture looks bullish, bearish, or neutral. Three are built in today:

StrategyWhat it looks at
EMA CrossoverWhether a fast moving average has crossed above or below a slower one.
SMA Trend FilterWhether the price has moved meaningfully above or below a single moving average.
ATR Volatility BreakoutWhether a bar's price move is unusually large compared to its recent typical volatility.

How to configure one

  1. Pick a strategy from the Strategy dropdown.
  2. Fill in its parameters — each field's label and help text explain what it means and what values are allowed; fields that reference a data field (like "which price to use") are themselves dropdowns, populated from the same field list the backend uses.
  3. Enter a Configuration Version label (e.g. cfg-v1) and click Save Configuration. A saved configuration cannot be edited afterward — save a new version instead, so past configurations are never silently changed.

Switching the Strategy dropdown clears any values you entered for the previous strategy — this is intentional, so a value that belongs to a different strategy's parameter can never be saved by mistake.

Why some fields are unavailable

Only fields the platform has actually implemented and tested (raw price/volume, plus the moving-average and volatility features above) appear anywhere. Nothing appears merely because it is planned.

Who can save

Anyone logged in can view strategies and their schemas. Saving a configuration requires the same "configuration-operators" group used elsewhere in this app (see Configuration Screens).

Strategy & Backtesting

The Backtesting screen lets you find out how a strategy would have performed on past price data, before you ever consider trusting it with real decisions.

A backtest is not a promise. It tells you how a strategy would have performed on the specific historical data you gave it — nothing more. Past performance never guarantees future results, and the numbers below are further limited by the data-quality notes in every result (see "Why results are not guarantees" below).

Key terms, in plain language

TermWhat it means
StrategyA rule that decides "bullish", "bearish", or "neutral" from recent prices.
ConfigurationThe specific parameter values (e.g. which moving-average lengths) a strategy is run with.
BacktestRunning a strategy's rule against historical bars to see what it would have done.
Trade simulationOne simulated buy-then-sell (or sell-then-buy) round trip the backtest generated — never a real order.
Net P&LProfit or loss after subtracting modeled costs (brokerage, slippage) — the "bottom line" number.
DrawdownHow far the simulated account balance fell from its highest point so far — a measure of how painful the ride was, not just whether it ended in profit. Calculated bar-by-bar (including while a trade is still open, "mark-to-market"), not only at the moment a trade closes — so a sharp dip that later recovered still shows up here.
Profit FactorTotal simulated profit divided by total simulated loss — above 1 means more was won than lost; below 1 means the opposite.
Trust LevelA label (currently always POC — "proof of concept") stating how much weight to give a result. It is never promoted to a higher level automatically just because a backtest ran successfully — see the callout below.
Every result you see today is labeled POC. That is deliberate, not a bug: passing tests and producing numbers is not the same as being ready to guide real decisions. A result only earns a higher trust label after further, separately-documented validation work — never automatically.

The workflow

  1. Discover — browse the strategy library and read what each one does.
  2. Configure — set its parameters (the exact same form as the Strategies screen — nothing is duplicated).
  3. Backtest — pick an instrument, date range, starting capital, and click Run Backtest.
  4. Review — read the results dashboard: summary numbers, equity curve, drawdown curve, and the full trade-by-trade ledger.
  5. Validate — compare against other strategies/configurations on the Compare screen.
  6. Activate for Research/Paper — mark a strategy "active" on the Strategies screen once you're satisfied. This still does not place any order.

Why results are not guarantees

  • Slippage is modeled as a simple flat percentage you choose — not a verified microstructure model. Every result labels this explicitly as a "model assumption".
  • The historical data used does not track stocks that were later delisted, which can make a strategy look better than it would have on the full, real universe of stocks at the time (survivorship bias).
  • If a result is ever built from SAMPLE_BAR data (see Why the current bars are SAMPLE_BAR, not trading-grade), it is marked "NOT SUITABLE FOR TRADING-GRADE PERFORMANCE CLAIMS" — today's backtests use historical/fixture data instead, never live SAMPLE_BAR.

Cost Model: what you're actually being charged in the simulation

Before running a backtest, you choose a Cost Model:

Cost ModelWhat it means
Flat PercentageMODEL ASSUMPTION — a single percentage you set, applied to every trade. Simple, but not a real cost schedule.
Indian Cash-Equity IntradayVERIFIED COST MODEL — the real NSE intraday charges: Securities Transaction Tax, exchange transaction charges, SEBI turnover fees, GST, and stamp duty, each calculated the way they actually apply (some only on buying, some only on selling). Brokerage itself stays a configurable estimate, since it varies broker to broker.

Every trade's result includes a cost breakdown you can expand to see exactly what each charge came to — never just a single lump "costs" number.

Comparing strategies

The Compare screen lists your past backtest results for a chosen strategy, lets you pick two or more, and ranks them by whichever metric you choose (Net P&L, Profit Factor, Return %, or Max Drawdown). It warns you if you try to compare results run on different instruments, timeframes, data quality, or cost models — comparing a Flat Percentage result against a Verified result would not be a fair comparison.

Watchlists

The Watchlists screen lets you save named lists of instruments for research use. This is not an order screen — there is no quantity, side, or order-related field anywhere on it.

Strategy Monitor

The Strategy Monitor screen shows each strategy's current research status and its latest backtest numbers at a glance. Pause Research/Resume Research only affects whether a strategy is included in research activity — it has no connection to live trading, which does not exist in this application.

Safety Rules

  • Do not enable LIVE trading.
  • Do not attempt to place orders — no order-placement code exists in this application.
  • Do not assume SAMPLE_BAR market data is trading-grade. It is not. See Market Data Concepts.
  • Do not paste credentials into source code, chat, or documentation.
  • Do not commit .env or frontend/.env.local.
  • Do not share your Dhan access token, Telegram bot token, or Discord webhook URL with anyone.
  • Do not change TRADING_MODE without understanding the consequences (see Trading Mode).
  • Do not attempt to bypass authentication or authorization checks.
  • Do not disable CSRF protection.
  • Do not modify risk controls just to make a test pass.

These rules reflect the current, honest state of the software — not an arbitrary policy. Several of them (order placement, live trading) are backed by the simple fact that the corresponding code does not exist yet, not merely a setting that's turned off.

Troubleshooting

Application does not start / app.bat closes immediately

Cause: usually a missing prerequisite (Python/Poetry/Node/npm) causing an early, immediate exit. Fix: re-run app.bat — as of the current version it pauses on every failure with a clear message instead of closing silently. If it still closes instantly, open a regular terminal and run app.bat from there so the error text stays visible. Verify: the missing tool now shows up in where python / where poetry / where node / where npm.

Python not found

Cause: Python isn't installed, or isn't on your PATH. Fix: install Python 3.12 and ensure "Add to PATH" was checked during install. Verify: python --version in a new terminal.

Poetry not found

Cause: Poetry isn't installed. Fix: install it per its official instructions. Verify: poetry --version.

Node/npm not found

Cause: Node.js isn't installed. Fix: install a current Node.js LTS release (npm is included). Verify: node --version and npm --version.

PostgreSQL unavailable

Cause: PostgreSQL isn't installed, isn't running, or your .env credentials don't match. Fix: confirm the service is running, and that POSTGRES_* in .env matches the user/database you created. Verify: http://127.0.0.1:8000/readyz reports "database": "ok".

Redis unavailable

Cause: Redis isn't installed/running, or REDIS_URL is wrong. Fix: install/start Redis, confirm REDIS_URL in .env. Verify: /readyz reports "cache": "ok".

Port 8000 already in use

Cause: another process (possibly a previous, un-closed backend window) is already listening on 8000. Fix: close the other process, or find and stop it (in PowerShell: Get-Process -Id (Get-NetTCPConnection -LocalPort 8000).OwningProcess | Stop-Process). Verify: re-run app.bat; step [6/8] should succeed.

Port 5173 already in use

Same pattern as port 8000 above, at step [7/8].

Login gives 401

Cause: wrong username/password, or your session expired. Fix: re-enter your credentials; confirm your account exists and is active. Verify: a correct login returns you to the app, not the login screen.

Login gives 403

Cause: almost always a timing issue — the page loaded before the backend was ready, so the security cookie was never set. See the full explanation in Login. Fix: reload the page once and try again; make sure you used app.bat and waited for its "both services are UP" message before opening the browser. Verify: the reload obtains a fresh cookie and login succeeds.

Frontend cannot reach backend

Cause: the backend isn't running, or frontend/.env.local's VITE_API_BASE_URL doesn't point at http://127.0.0.1:8000. Fix: confirm the backend window is running and /healthz responds; confirm the env value. Verify: the browser's network tab shows successful requests to 127.0.0.1:8000.

CORS error

Cause: you're accessing the frontend from a URL other than http://localhost:5173 or http://127.0.0.1:5173 — the only two origins the backend trusts in development. Fix: use exactly one of those two URLs.

CSRF error

See "Login gives 403" above — same underlying cause.

Dhan authentication failure

Cause: the configured Client ID / Access Token was rejected by Dhan itself. Fix: regenerate/verify the credential in Dhan's own developer portal, then re-save it in Settings. This is not something the application can fix — it reflects Dhan's own response. Verify: Test Connection reports "Connected."

No market data

Cause: either Dhan isn't configured/working (see above), or you haven't clicked Refresh Quotes yet, or the market is closed. Fix: check Connection Health first, then confirm market hours. Verify: the Observed Instruments table populates after a successful Refresh during market hours.

Market data is stale

Cause: more than ~2 minutes have passed since the last successful Refresh. Fix: click Refresh Quotes again. This is expected behavior for an explicit-trigger system, not an error.

Recent Bars are empty

Cause: no successful quote fetch has happened yet. Fix: click Refresh Quotes at least once during market hours.

Volume shows —

Not an error — see Market Data Concepts.

Database migration error

Cause: PostgreSQL isn't reachable, or your database user lacks permissions. Fix: re-check the database setup steps in Installation.

npm dependency error

Cause: a corrupted or partial node_modules install. Fix: delete frontend/node_modules and re-run npm install (or just re-run app.bat, which detects the missing folder and reinstalls).

Poetry dependency error

Cause: a corrupted virtual environment. Fix: delete the .venv folder and re-run poetry install (or re-run app.bat).

Browser cannot open the application

Cause: the frontend server isn't actually running yet, or crashed. Fix: check the "IntraDay Frontend" window for error text; confirm app.bat's step [7/8] reported success.

Safe Shutdown

  1. Stop the frontend: close the "IntraDay Frontend" window, or click inside it and press Ctrl+C.
  2. Stop the backend: close the "IntraDay Backend" window, or click inside it and press Ctrl+C.
  3. PostgreSQL / Redis: only stop these yourself if you manage them as separate native services and want to free resources — the application does not require you to stop them between sessions, and other software on your machine may depend on them staying up.

Restarting everything

Simply double-click app.bat again — it's safe to re-run any time.

Checking for orphaned processes

If a window was closed without stopping its process cleanly, in PowerShell:

Get-NetTCPConnection -LocalPort 8000,5173 -ErrorAction SilentlyContinue

If either port still shows a listener you didn't expect, find and stop that process by its PID with Stop-Process.

Do not manually kill PostgreSQL or Redis processes unless you specifically manage them yourself and understand the consequences for any other software using them.

FAQ

Do I need programming knowledge?

Not to install and use the app day-to-day — app.bat handles the technical startup. Understanding what the screens mean helps, which is why this guide exists.

Do I need to run Django manually?

No — app.bat starts it for you.

Do I need to open two terminals?

No — app.bat opens both server windows for you automatically.

What is app.bat?

A Windows script in the project root that checks prerequisites, installs dependencies if needed, and starts both the backend and frontend, verifying each is actually reachable before telling you it's ready.

Why are there multiple command windows?

One runs the backend, one runs the frontend, and (briefly) one is the launcher itself. This is intentional — each server needs its own window since both run continuously.

Why can't I see live signals?

Signal generation isn't implemented yet, and the current market data is classified SAMPLE_BAR — not reliable enough to build signals on. See Market Data Concepts.

Why can't I trade yet?

No order-placement code exists anywhere in this application yet. This is a deliberate, staged approach to building the platform safely.

Why does volume show —?

To avoid showing a fabricated number. See Market Data Concepts.

Why is Dhan authentication failing?

Usually because the configured Access Token is invalid or expired — check it in Dhan's own developer portal.

Can I use fake data?

The application never fabricates market data. Automated tests use clearly-fake data internally, but the running application only ever shows real data it actually fetched, or nothing.

Can I test without Dhan?

Yes — Login, Configuration, and Settings all work without any Dhan credential. Only the Market Data screen's live-fetch feature needs one.

Is this production-ready?

No. It has no Docker deployment, no order/trading capability, and its market data is explicitly not trading-grade yet. It is a real, working development-mode application, not a demo.

Can I run this on another Windows PC?

Yes, as long as it has the prerequisites in Before You Start installed. app.bat resolves paths from its own location, so it doesn't need a fixed folder location.

Real trading with real money. Not implemented; structurally blocked outside production configuration.
