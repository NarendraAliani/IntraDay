| Kill switch / emergency square-off for open positions | `BLOCKED` — now with a PRECISE, understood reason (Checkpoint 44) | Investigated concretely this checkpoint, not merely re-stated. The actual blocker: `evaluate_order_risk()` checks `kill_switch_status is HALTED` FIRST, unconditionally, for EVERY order - entry or exit alike (Decision from Checkpoint 34, re-confirmed by Checkpoint 34's own "kill switch cannot be bypassed" test). This means `PositionMonitorService`'s exit orders (Checkpoint 43/44) would ALSO be rejected by a halted kill switch, exactly backwards from what "emergency square-off" needs (close positions BECAUSE the kill switch fired). Implementing this correctly requires the risk engine to distinguish "block NEW entries" from "permit CLOSING an existing position" - a genuine, safety-relevant design decision (which orders count as "closing"? partial exits? by how much quantity?) that this checkpoint's remaining time did not allow to design carefully. Per this project's own "if something is unsafe, do not implement it merely because it is technically possible" discipline, no rushed change was made to the risk engine's kill-switch check (a safety-critical path) this checkpoint. **Next action**: a dedicated, reviewed checkpoint adding an `order_intent.is_reducing_position: bool` (or equivalent) concept the risk engine's kill-switch check can key off, with its own test suite proving a reducing order is never blocked by HALTED while a non-reducing order always still is. |

Reconciliation now also triggers when an automatic exit fires, not only on a new entry. 2 new tests: a contract test proving zero positions means zero evaluation (no fabricated activity), and a full stop-loss-triggering scenario proving a real open position (with a real `ExitPlan` attached via `attach_exit_plan()`) is automatically exited within one scheduled tick, producing a second real paper order. Proven by ONE complete end-to-end test through the real orchestration path (`test_full_entry_to_monitored_exit_lifecycle_through_real_orchestration`): signal → entry order → fill → position with a real `ExitPlan` → 3 price updates → TARGET_1 (partial) → TARGET_2 (partial) → TARGET_3 (full close) → 4 total orders, complete audit trail. **Two real bugs found and fixed by this test** (see Decisions 191-192): a partial-exit-fraction basis bug that left rounding-drift residuals instead of closing exactly, and a Python `Decimal('0') or x` falsy-zero bug that would have resurrected a fully-closed position as still-open on its next load. |

## What changed since Checkpoint 34/35's registers

- **Closed this checkpoint**: nothing was fully closed to `IMPLEMENTED_AND_TESTED`
  at the "operates automatically in production" bar — the new bridge is
  real and tested but explicitly not wired to a live trigger (see P0).
  Overstating this as "done" would be exactly the dishonesty this
  checkpoint's principles forbid.
- **Newly identified this checkpoint**: the market-data-classification
  enforcement gap (P1) — did not exist as a distinct line item before,
  because no automated signal-to-order pathway existed for it to matter
  yet.
- **Explicitly not re-audited this checkpoint** (carried forward
  unchanged, flagged so silence isn't mistaken for resolution): instrument
  master coverage, session/holiday calendar correctness, clock-drift
  monitoring, accessibility validation, failure/recovery matrix.
